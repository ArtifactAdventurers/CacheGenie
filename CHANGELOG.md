## [Unreleased]

### Fixed
- `index-sync` incremental updates no longer peg a CPU core for hours in a silent post-read phase on a large diff. An "incremental" chunk is normally tiny, but a post-gap catch-up (or a large index publish) can carry hundreds of thousands of records, and the apply phase ran them through the **row-by-row** `IndexSyncWriter`: one `SELECT id FROM meta_artifacts WHERE gid=? AND aid=?` point lookup per distinct artifact (plus a single-row `INSERT` per version). DuckDB serves those filtered lookups by **full table scan** — so the apply degraded to O(artifacts) scans of a multi-million-row table (a thread dump showed `main` stuck in `IndexSyncWriter.artifactId` → `executeQuery`, 100% CPU). The ADD records are now applied through the same **set-based staging merge** the full bootstrap uses (`IndexStageLoader`: stage via the Appender, then bulk-create artifacts and bulk-insert versions with set-based anti-joins — one scan apiece instead of O(N)). Incremental removals (`ARTIFACT_REMOVE`, typically few) are applied row-by-row via `IndexSyncWriter` and their affected artifacts' `latest`/`release` refreshed in one pass. The phase now prints `Merging N staged version(s) (set-based)…` so it is no longer silent.
- `index-sync` artifact-summary refresh (`generated`/`latest`/`release`) is now **set-based** on the incremental path too. The previous per-artifact `UPDATE` carried three correlated `arg_max(version, published)` subqueries over `meta_versions WHERE ga_id = ?`; with no standalone index on `ga_id` (the `(ga_id, version)` PK doesn't reliably serve a `ga_id`-only predicate in DuckDB) each degraded to a full scan, so refreshing many artifacts was itself an O(N)-scan trap (the next wall after the apply-loop fix above). `IndexSyncWriter` now records the touched `ga_id`s and `refreshSummaries()` recomputes them in one grouped aggregate over `meta_versions`, preserving the exact `arg_max`/`-SNAPSHOT` semantics. `db optimize` also adds `idx_meta_versions_ga` on `meta_versions(ga_id)`, which additionally speeds up `removeVersion`, `markPomAsMissing`, and `loadVersions`.
- `RawPomParser` (the `graph mine` parser) no longer counts POMs `bad` just because they reference an unresolvable external DTD/entity. Its `DocumentBuilderFactory` now disables external DTD loading and external general/parameter entities (and enables secure processing), so POMs carrying a `DOCTYPE`/`SYSTEM` reference such as activemq's `locator.ent` parse instead of failing with `No such file or directory`. Also hardens the parser against XXE — it never fetches external resources during a crawl.
- `graph mine` worker tasks can no longer die uncounted from **any** unexpected exception. The fetch/parse/enqueue body is now wrapped so an unchecked exception (the `${VERSION}` URI case was one instance; parser/DOM edge cases are others) is caught, counted in a new `errors` bucket (shown live in the progress suffix and the final summary), and logged with the offending coordinates — instead of vanishing and leaving `visited` climbing while every outcome counter froze. The breakdown now reconciles (`visited == mined + missing + transient + bad + errors`), and a sustained run of unexpected errors feeds the same circuit breaker that aborts on transient failures, so a systemic code/data fault stops the run rather than mining nothing for hours.
- `graph mine` no longer lets worker tasks die uncounted on unresolved property-placeholder versions. Coordinates like `ai/optiscan/optiscan/${VERSION}` leak into the catalogue as literal text; `PomFetcher.download` called `URI.create` on the resulting URL, which threw an unchecked `IllegalArgumentException` (`Illegal character in path` for `$`/`{`/`}`) that escaped the `IOException`-only catch, failed the worker task, and incremented **no** outcome counter — so `visited` advanced while `mined`/`missing`/`transient`/`bad` did not (the count "gap" beyond the ~10k write-queue buffer), and the same versions threw again every run. `PomFetcher.fetch` now detects `${...}` placeholders in any coordinate up front and a defensive `catch (IllegalArgumentException)` in `download` backstops any other malformed URL; both classify the version `NOT_FOUND` so it's marked `missing_pom` and skipped on future runs instead of retried forever.
- `graph mine` no longer fails the vast majority of fetches with `too many concurrent streams`. `PomFetcher`'s shared `HttpClient` was built with `HTTP_2`; the JDK client multiplexes every HTTP/2 request onto a **single** connection per origin and won't open a second, so once in-flight requests exceeded the server's `SETTINGS_MAX_CONCURRENT_STREAMS` (easy with a large `--threads` pool) it threw `too many concurrent streams` — which `download` then mis-classified as `TRANSIENT`. That produced runs that were ~95%+ "transient" (e.g. `mined 1226 / transient 31257`, `missing 0`) with no actual server problem. Switched the miner's client to `HTTP_1_1`, which pools multiple keep-alive connections (one request each) and scales with the worker count without a per-connection stream cap.
- `graph mine` now **aborts when the DuckDB writer thread dies** instead of sailing on. Previously a fatal exception in the drainer only set `writerDead`, which made `enqueue` silently drop every subsequent POM — the run kept fetching (visited/ETA advancing) while `mined` was frozen and nothing was persisted. The drainer's catch now trips the shared `aborted`/`abortReason` stop signal (carrying the writer's exception message), so the run stops loudly and re-runs resume from what was actually written.
- `graph mine` now **aborts fast on systemic failure** instead of grinding through the whole worklist mislabelling everything `transient`. A circuit breaker tracks consecutive transient failures with no intervening success (reset on any OK/NOT_FOUND, since a 200 or a definitive 404 proves the pipe works) and stops the run once it crosses `TRANSIENT_ABORT_STREAK` (500), printing a clear cause (endpoint/network/HTTP-protocol) rather than the 429 message. The 429 abort and this breaker now share one stop signal (`aborted` + `abortReason`); progress is saved either way, so a re-run resumes.
- `graph mine` no longer OOMs on a large/unbounded backlog. The old path materialised the **entire** worklist into one `List` and then pre-submitted every task to an unbounded `ExecutorService` queue while retaining every `Future` — on a full-Central run (~14.8M versions) the heap filled during task submission (`OutOfMemoryError` at the submit loop), before mining made real progress. Mining now **streams** the worklist in bounded keyset pages (`MetaRepository.selectVersionsToMineAfter`, ordered by `(gid,aid,version)`, cursor-paged so already-mined/failed rows don't reappear or loop) and processes one page at a time through a reused worker pool, so memory is constant regardless of catalogue size and `--limit` is no longer required just to avoid running out of heap. Per-page reader/writer phases stay disjoint (a read connection is never open against `graph.db` at the same time as the mining writer), preserving the existing single-connection invariant.

### Added
- New `metadata` (`gen-metadata`) command synthesises `maven-metadata.xml` files into the local Maven repository (`~/.m2/repository`) straight from the discovery catalogue (`meta_artifacts`/`meta_versions`) — **no network**. `graph mine` fetches only the `.pom`, so the local repo has POMs but no version metadata; an *offline* Aether resolve then can't handle version ranges or `LATEST`/`RELEASE`. This rebuilds that metadata from data `index-sync` already has: one `maven-metadata-<repo-id>.xml` per `(groupId, artifactId)` (default id `central`, matching the `Resolver`'s remote, so `SimpleLocalRepositoryManager` finds it; `--also-plain` also writes plain `maven-metadata.xml`). `<versions>` are written in publish-date order (best-effort deployment order; cosmetic for resolution since Aether re-sorts), and `<latest>`/`<release>` come from the catalogue (newest by publish date = Central's "last deployed"). Functionally equivalent to Central's metadata for resolution, **not** a byte-for-byte copy (`<lastUpdated>` is stamped now; exact version ordering may differ). Backed by `MetaRepository.streamArtifactMetadata`, which groups a single ordered join on the client so heap stays bounded regardless of catalogue size. `-gav <group[:artifact]>` scopes it; omit to do the whole catalogue. Pairs with offline resolution so a per-GAV graph can be built from local POMs without touching Maven Central.
- `graph mine` gains `--limit <n>` (pushed into `selectVersionsToMine`'s SQL) for polite, resumable chunks — pair with cron to drip a large backlog over days; re-runs skip already-mined versions. New `MINING.md` documents running `mine` at scale via the verified Google GCS mirror (`-r https://maven-central.storage-download.googleapis.com/maven2/`), rate guidance, and resume-on-429 / chunked patterns.
- New `graph push-neo4j` command MERGEs CacheGenie's DuckDB graph delta into an **existing** Neo4j graph (e.g. a loaded Goblin dump) directly over Bolt, augmenting it in place — the primary hybrid flow: Neo4j stays the canonical graph, DuckDB is the working store, and CacheGenie tops Neo4j up with whatever it freshly mined/resolved. Writes in Goblin's schema with `MERGE` throughout (idempotent + additive), batched write transactions (`--batch-size`), `--since` to scope by publish date, `--uri/--user/--password` for the connection. Uses the **Apache-2.0** Neo4j Bolt driver (`org.neo4j.driver:neo4j-java-driver`) — no GPL entanglement, since that applies to the Neo4j server, not the driver. See `HYBRID-NEO4J.md`.
- New `graph export-neo4j` command exports the graph as `neo4j-admin import` CSVs in **Goblin's schema** (`:Release`/`:Artifact` nodes, `relationship_AR` versioning edges, `(Release)-[:dependency {targetVersion, scope}]->(Artifact)` edges), enabling the hybrid model: DuckDB stays the system of record (ingest, mining, relational meta, analytics) and Neo4j becomes an optional read-side for graph traversal + Goblin **Weaver** interop. `GraphRepository.exportNeo4jCsv` writes the four CSVs via DuckDB `COPY` (read-only on the DB); `--with-metadata` adds name/url/scmUrl to Release nodes from `pom_meta`. Output is Weaver-compatible and conceptually mergeable with a loaded Goblin dump. CacheGenie never embeds/links Neo4j (only writes CSVs), so no GPLv3 entanglement. See `HYBRID-NEO4J.md`.
- New `graph import-goblin` command seeds `artifacts`/`dependencies` from a [Goblin](https://zenodo.org/records/15481588) dependency-edge CSV export — a pre-computed, Aether-resolved snapshot of the whole Maven Central graph (equivalent to a full `graph deps` run) — in minutes with zero Central traffic. Set-based DuckDB load via `GraphRepository.importGoblinEdges` (`read_csv_auto` → distinct-GAV insert with sequence ids → edge join, `INSERT OR IGNORE` so idempotent). Range/property `targetVersion` edges are skipped unless `--include-ranges`. See `GOBLIN-IMPORT.md` for the Neo4j-4.x load + Cypher CSV export steps; keep current afterwards with `graph mine --since <snapshot>`.
- New raw-POM **mining** pipeline as a polite, scalable alternative to `graph deps`' Aether effective-POM resolution (which fans out into parent/BOM fetches per artifact and trips Maven Central's 429s):
  - `graph mine` — for each un-mined catalogue version (no `pom_meta` row, not `missing_pom`) it fetches **only the `.pom`** via `PomFetcher` (serves from the local `~/.m2` repository if present, else one plain HTTP GET saved into `~/.m2` in Maven layout — no Aether, no checksum request, no descriptor read, so no parent/BOM fan-out) and parses it with the new thread-safe `RawPomParser` (per-thread `DocumentBuilder`) into a `MinedPom`. Stores the **raw, as-declared** contents — dependencies, `dependencyManagement`, parent ref, properties, scm, organization, developers/contributors, licenses — across new tables (`pom_meta`, `direct_dep`, `dependency_management`, `pom_properties`, `pom_developers`, `pom_licenses`) via `GraphRepository.MiningWriter`. Parents/BOMs are never downloaded per-child; each is mined once as its own catalogue node. Paced/threaded/429-aborting like `graph deps` (`--rate`, `--threads`, `--since`, `--gav`, `--list`); `--rate` maps closely to real load here since it's ~1 request per artifact.
  - `graph resolve` — first-cut `PomResolver` that turns mined POMs into concrete `dependencies` edges: walks the parent chain and import-scope BOMs to fill managed versions, interpolates `${...}` properties, and writes resolvable direct edges (setting `pom_meta.deps_resolved`). Idempotent; `--all` re-resolves everything. Known gaps (documented): version ranges, profiles, exclusions, relocation, and inherited project metadata coalescing.
  - Schema keys `direct_dep`/`dependency_management` by `(artifact_id, ord)` so every declared row is kept verbatim. `db optimize` now also creates `idx_pom_meta_parent`, `idx_direct_dep_coord`, `idx_depmgmt_coord`. See `DB_SCHEMA.md`.
- `graph deps` gains `--rate <req/min>` (shared `RateLimiter`, one permit per artifact; `0` = unlimited) to proactively throttle descriptor reads across all `--threads`, complementing the reactive 429 abort. Note: the effective-POM read still fans out, so true request rate is a multiple of `--rate`.
- `-P/--progress` lines can now carry a **live running-stats suffix** via `Progress.stats(Supplier<String>)`, appended to every emitted line and the final `done` summary. Wired into `graph mine` to show the cumulative outcome breakdown in real time, e.g. `[progress] Graph mine: 3135000/3135547 (928/s, ETA 0s) [mined 67829, missing 155, transient 3067053, bad 388] — zone.ien.utils:cmp-icon:2.6.0`. This makes a run that is mostly transient failures (throttling/5xx) obvious while it is happening instead of only in the final summary. The supplier is generic, so other long-running commands can adopt it.
- `-P/--progress` lines now show `n/total` and an **ETA** when the command knows the total work upfront (`Progress.total(...)`). Wired into `graph deps` (total = selected worklist size), e.g. `[progress] Graph deps: 1074/52310 (9/s, ETA 1h36m)`. Commands without a known total keep the `n processed` form.
- `graph deps` now classifies descriptor-read failures (`Resolver.directDependencies` returns a `ResolveOutcome`): only a genuine **not-found** marks the version `missing_pom`; **transient** errors (5xx/timeout/connection) are left unmarked for retry (so rate-limiting/network blips no longer poison data by flagging good artifacts as missing); and the **first HTTP 429** aborts the whole run with a clear message — a single overload of Maven Central stops the crawl rather than hammering it. Progress so far is saved; re-run to continue.
- `graph deps` gains `--since <dur>` (e.g. `30d`, `12w`, `24h`) to select versions *published within a window* (using `meta_versions.published` from `index-sync`), with or without a `--gav` filter — so "graph the dependency trees of everything released in the last month" is one command. `--gav` is now optional (use `--since` alone to span the whole catalogue). Selection is one SQL query (`MetaRepository.selectVersionsToGraph`) that also excludes missing-POM and already-graphed versions. `graph deps --list` (alias `--dry-run`) prints the selected versions and count and exits without graphing — a preview of the worklist.
- New `graph deps` subcommand: builds the **direct**-dependency graph for targeted `--gav` selectors driven from the discovery catalogue. Per version it reads the effective direct dependencies (Aether `readArtifactDescriptor` — managed versions/BOMs/properties applied, but no transitive collection) via `Resolver.directDependencies`, and persists edges via `GraphRepository.persistDirect`. Transitive trees are computed on demand with recursive CTEs rather than resolved-and-stored per artifact, which avoids re-walking shared subtrees across the ecosystem. Skips already-graphed and `missing_pom` versions, and marks a version `missing_pom` when its descriptor can't be read (internal/test modules, unresolvable parents) so re-runs skip it. Descriptor reads run on a worker pool (`--threads`, default 8, per-thread `Resolver`); DB writes are serialised under one lock (DuckDB single-writer). Failed reads are logged at DEBUG (was WARN) so they don't drown the output.
- `index-sync` full bootstrap now bulk-loads via DuckDB's Appender into a staging table then merges set-based (`MetaRepository.IndexStageLoader`): the ~100M file-records are collapsed to distinct versions once and the index is built once, replacing the per-row `ON CONFLICT` path that took ~24h on the first run. Incremental updates still apply their small diff row-by-row (so ARTIFACT_REMOVE is honoured). The staging table transiently grows `graph.db` — run `db compact --rewrite` afterwards to reclaim it.
- `index-sync` now records richer per-version fields from the index: `packaging`, `file_extension`, `file_size`, `sha1`, `sha256`, `has_sources`, `has_javadoc` (new columns on `meta_versions`). Captured per version from the main artifact file (the largest classifier-less record); per-classifier checksums are not stored. Class-name contents are deliberately not ingested (too large). Useful for verifying hydrated jars and knowing what exists before downloading.
- `index-sync` now also fills the artifact-level summary so an index-only DB isn't missing it: it stamps `meta_artifacts.generated` and derives `latest`/`release` as the newest version by publish date (`release` excludes `-SNAPSHOT`). Done set-based in the full merge and (since the fix above) set-based over the touched artifacts on incremental.
- `index-sync --limit <n>` stops after N records and does not persist sync state, for quickly smoke-testing the full ingest path (pair with `-c <scratch-cache>` to keep the real DB untouched).
- New `index-sync` (`central-sync`) command: discover artifacts and versions from the repository's **published Maven index** (the maven-indexer format Central publishes under `.index/`) instead of crawling HTML directory listings. The first run downloads the full index; subsequent runs pull only the incremental chunks published since, tracked via local state under `~/.m2/cachegenie/work/indexer`. `--full` forces a complete re-pull. Records stream straight into the DuckDB meta tables. Uses the dependency-light `org.apache.maven.indexer:indexer-reader` (7.1.6); `HttpResourceHandler`/`FileWritableResourceHandler` provide the remote/local resource access, `IndexerSyncAction` drives it, and `MetaRepository.IndexSyncWriter` does the streaming upsert. The HTML `scan` remains for targeted `--gav` lookups and immediacy.
- `index`/`scan` undirected discovery now applies a freshness gate: `--max-age <dur>` (e.g. `7d`, `24h`, `30m`; `0` = always check; default `7d`) skips re-fetching `maven-metadata.xml` for any artifact whose metadata was last written within the window. The check happens before the fetch (no request, no descent) using `meta_artifacts.generated` loaded once into an in-memory map. Explicit `--gav` requests always check (gate bypassed). The scan summary reports how many were skipped as fresh.
- `index`/`scan` random-walk discovery now crawls top-level groups concurrently. `--threads <n>` (default 8) sets the worker count; `--rate <req/min>` (default 100) is now the **total** request budget shared across all workers via a single `RateLimiter`, so politeness is preserved while hiding per-request latency (previously the crawl was single-threaded and stuck at roughly one request per second regardless of `--rate`). Each worker uses its own `MavenMetaDataFactory`/parser since `DocumentBuilder` is not thread-safe. Added `NavigatorPolicyBuilder.rateLimit(RateLimiter)` so policies can share one limiter.
- `index`/`scan` gains a `--rate <req/min>` option to set the crawl's rate limit (default 100 requests/minute), so the remote-repository politeness throttle is configurable from the CLI instead of hardcoded in `IndexBuilder`.
- Global `-P/--progress` option that emits throttled progress messages to stderr during long-running commands (index/scan, meta/fetch, graph cache, analyse, hydrate).
- `graph cache` now resolves and persists the dependency graph for every artifact in the local cache to the DuckDB graph (skipping artifacts already present), instead of only listing them.
- Discovery metadata is now stored in the DuckDB database (`meta_artifacts` and `meta_versions` tables) via a new `MetaRepository`, alongside the dependency graph, so meta and graph can be queried together. See `DB_SCHEMA.md`.
- `graph stats` now reports discovery-metadata statistics (tracked group:artifacts, discovered versions, versions with missing POMs, average versions per artifact, top artifacts by version count and by missing POMs) and ensures both the graph and meta schemas exist so it works after a `scan`-only or `graph`-only run.

### Changed
- `Resolver` now uses Aether's **simple** local-repository manager (set once at construction) instead of the default "enhanced" one. The enhanced manager tracks per-artifact remote origin and re-verifies cached artifacts against the configured remote over the network when the recorded origin doesn't match (the `… cached from a remote repository ID that is unavailable …` log line); the simple manager trusts the local cache as-is, removing a network round-trip per already-cached artifact. Speeds up resolve-heavy work like `graph deps`. Falls back to the enhanced manager if the simple one can't be created.
- `index`/`scan` now **merges** discovered metadata instead of mirroring it: it adds versions missing since the last scan and refreshes the artifact's top-level fields, but no longer deletes versions or overwrites a version's `missing_pom`/`published` (so flags set by `fetch` survive a re-scan). Implemented as `MetaRepository.mergeDiscovered`; `handleMeta` uses it in place of the full-mirror `save`.
- `index`/`scan` prints a summary at the end: metadata files found, new artifacts vs. already-known, and total new versions added (across new and updated artifacts).
- The `db` command is repurposed from a legacy `.properties`→CSV dumper into a DuckDB management command with subcommands: `compact` (CHECKPOINT + VACUUM to reclaim space), `optimize` (secondary indexes + ANALYZE), `views` (create the `gav`, `dependents`, and `version_ranges` convenience views), and `export` (COPY tables + `version_ranges` to parquet/csv/json). The old per-artifact version date-range dump (`range.db`) is now the `version_ranges` view.
- `index`, `meta`, `graph` (pattern resolve), `meta-csv`, and `update` now read/write discovery metadata through `MetaRepository` (DuckDB) instead of `.properties`/`.json` files.
- `migrate-meta` is repurposed as a one-time importer: it loads existing `.properties` and `.json` meta files into the DuckDB meta tables (previously it converted `.properties` to `.json`).
- Malformed POMs now log a WARN naming the file and are skipped, instead of emitting a raw `[Fatal Error] ...` line to stderr; processing continues. A custom SAX `ErrorHandler` replaces the JAXP default.
- Routed `CacheAction`'s stray `System.out`/`printStackTrace` output through SLF4J for consistent logging.

- `migrate-meta` is now resumable. It streams records straight into DuckDB (no longer building an in-memory map of every record, which exhausted the heap on large caches with hundreds of thousands of meta files), and skips coordinates already imported so an interrupted run can be restarted without redoing work. For `metadata.json` the coordinate is derived from its Maven-style path, so already-imported files are skipped without being re-read. A new `--fresh` flag clears the meta tables for a full re-import.

### Fixed
- `graph deps` throughput was capped at a few artifacts/second regardless of `--threads`, because each persisted artifact (and each missing-POM mark) opened a fresh DuckDB connection, committed, and closed — all serialised behind the single-writer lock. Added `GraphRepository.DirectWriter`, which holds one connection open for the whole run with cached artifact ids, reused prepared statements, and batched commits; `graph deps` now writes through it. Resolution (parallel) becomes the limit again, so `--threads` scales.
- `migrate-meta` discarded a leading `null`/literal value when hand-parsing `metadata.json`, so versions with no publish date (e.g. missing-POM versions) read the next key name as their date and logged `Failed to parse published date 'missingPom'`. `extractJSON` now distinguishes quoted strings from unquoted literals.
- `migrate-meta` hit `Duplicate key ... violates primary key constraint` writing versions, because it deleted and re-inserted the same key within one transaction (a DuckDB ART-index limitation). Version writes now use `INSERT ... ON CONFLICT DO UPDATE`, which also makes re-running the import idempotent.
- Logging was silent in the shaded jar: `logback.xml` lived only in the pom-packaged reactor root (which ships no jar), so `-l/--log` reset the logger context to zero appenders. `logback.xml` now ships in the `cli` module, and `RootCmd` falls back to a basic console configuration if it is ever absent.
- `migrate-meta` was extremely slow on large caches because `MetaRepository.save` opened a new DuckDB connection per record. Added `MetaRepository.saveAll`, which reuses a single connection and commits in batches; the importer now uses it and reports progress under `-P`.

### Removed
- The unused `ListAction`, `IndexStatus`, and `IndexStats` classes (and the `TestIndexStatus` test), which were the last code that read the legacy on-disk `.properties` meta files. With `analyse meta` repointed at DuckDB, no command reads those files any more, so the legacy `~/.m2/cachegenie/*.properties` and `~/.m2/cachegenie/meta/` trees can be deleted. (`MavenMetaData.load(File)` remains but is now unused.)
- The `migrate-meta` command (and `MigrateMetaAction`), the one-time importer that loaded legacy `.properties`/`metadata.json` files into the DuckDB meta tables. The migration is complete; metadata now lives solely in DuckDB. (The `MetaRepository` bulk-writer and `MavenMetaData.loadJSON` that only served it are now unused.)
- `CreateDBAction`, the legacy `db` command implementation that read `.properties` files (no longer produced) and dumped CSV `index.db`/`range.db` files. Replaced by `DBAction` and the new `db` subcommands.
- `MavenMetaData.save(File)`, the only code that wrote a legacy meta file (the `.properties` form). It had no callers — metadata is now written exclusively to the DuckDB meta tables — so nothing in the tool writes `.properties` or `metadata.json` meta files any more; those formats are read-only import sources for `migrate-meta`.
